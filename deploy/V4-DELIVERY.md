## 实现与数据

前端继续使用 React、TypeScript 和 Vite，后端继续使用 FastAPI。Supabase 验证已确认邮箱的登录会话，私有项目数据写入 PostgreSQL，PDF 存入原有私有 Storage 桶。V4 不依赖 Render 实例磁盘保存用户记录。只有公开职位的短期缓存随进程重启失效。

- **推荐**使用现有 DeepSeek JSON 客户端。模型分析经历与相邻职业方向，服务端逐条检查证据是否为简历原文、方向分类是否合法。项目、简历、目标、阶段、语言和测评版本决定推荐的复用条件。模型输出无效时返回错误，保留先前结果。
- **招聘**由后端请求三个固定企业招聘板，简历和测评答案均留在应用内。根据来源 ID 去重，保留来源给出的公司、岗位、地点、用工类型、详情与申请地址；招聘说明作为纯文本展示。普通查询使用十分钟缓存，主动刷新和失败重试至少间隔三十秒。查看详情和导入 JD 时重新请求具体职位，已关闭职位会提示。只接受符合企业与职位 ID 的 HTTPS Lever 地址。地区与资历筛选依据招聘文本，香港或内地的校招和实习结果可能为空。[Lever 官方接口](https://github.com/lever/postings-api)
- **来源选择**核对了 Greenhouse 和 Adzuna 官方说明。本版只启用 Lever。Greenhouse 同样以企业招聘板为单位，公开 GET 可读取；Adzuna 需要注册密钥。未购买招聘服务。[Greenhouse Job Board API](https://docs.greenhouse.io/job-board.html) · [Adzuna API](https://developer.adzuna.com/)
- **测评**四个维度各三题，每维度有一道反向题。每题转换为 0–4 分，每维度总分换算为 0–100。离中点最远的维度和方向决定画像，同分按固定维度顺序选择，全部中性时使用“情境观察者”。报告依据规则和模板生成，职业偏好与履历事实分开展示。
- **复盘**每条记录包含用户选择的面试日期、问题、可选回答、反思和反馈。一次明确的分析操作将整场问题发至模型。可选携带当前项目简历。每个报告版本保存对应问题快照，空回答由服务端屏蔽评价。每份最多 12 题，限制输入长度，超限提示缩短材料。AI 不可用时仍可记录、编辑和查阅历史。
- **存储与权限**复用 `career_private.projects` 的 JSONB、版本号和行级安全策略。V4 项目和账户级探索记录使用独立命名空间，V3 材料入口使用受账户归属限制的只读查询。写操作检查版本号。没有新表、生产数据回填、批量迁移或重置。原有 `career_private.calls` 继续承担每日十次额度的原子预留。

## 后续成本统计

测评计分、测评历史、职位查询、查看已保存的报告均不消耗模型额度。新增的模型功能是职业方向推荐与面经复盘，导入职位后运行的 JD 匹配仍使用原模块额度。用量事件记录功能、模型、开始时间、账户及关联项目、成功状态、缓存状态和供应商返回的原始 usage。无供应商 usage 的失败和应用缓存命中不填估算值。

最后一次完整真实测试中，推荐的输入／输出为 241／282 tokens，初次复盘为 368／873，重新复盘为 376／817。相同输入复用推荐产生一条缓存事件，账户额度未增加。这些数值仅代表该轮测试。

服务端可用受控数据库连接执行下面的只读查询，再按现有运维流程导出 CSV。查询只导出用量字段。

```sql
select user_id, state->>'project' as project_id,
       state->>'feature' as feature, state->>'model' as model,
       state->>'started' as requested_at, state->>'success' as success,
       state->>'cache' as cached,
       state->'usage'->>'prompt_tokens' as input_tokens,
       state->'usage'->>'completion_tokens' as output_tokens,
       state->'usage' as provider_usage
from career_private.projects
where app_id = 'codex_v4_exploration' and name = 'usage'
order by revision;
```
